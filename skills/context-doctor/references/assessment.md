# Assess and improve agent guidance

Read this for semantic assessment, remediation or prioritisation beyond direct integrity findings.

## Investigate from a task

Walk through what the agent would need to find, decide, execute and verify on one representative engineering task. Use an existing task, package or change when possible. Trace from the entry instructions and record where a reasonable agent would use the wrong command, violate a local constraint, need to guess or miss a necessary check. Verify the claim against the closest owning source, configuration, CI job or project policy. For missing knowledge, show the task step that becomes unreliable and inspect whether a discoverable authoritative source already covers it.

| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stale claim                         | Trace the exact instruction to executable configuration, source or history. Check for legacy callers before removing the reference.                       | Point to the current source of truth and clarify the affected scope.                                                                                                                |
| Weak actionability                  | Try to identify command, directory, preconditions, safe effects and expected success evidence without running untrusted examples.                         | Specify the missing operational fact or make the existing trusted procedure discoverable.                                                                                           |
| Apparent duplicate                  | Compare audience, trigger, authority, operational meaning and updates. Exact copies can be intentional. Different wording can still duplicate one policy. | Consolidate when the same audience reliably reaches one authoritative version. Keep a scoped reminder when it protects independent entry paths or clarifies a different obligation. |
| Apparent contradiction              | Check whether the rules can both govern the same decision. Trace path, task, environment and effective precedence.                                        | Clarify applicability first. Seek approval when intent or ownership determines the correct policy.                                                                                  |
| Excess upfront context              | Identify what an agent must know before acting and what can be safely retrieved later. ## Decide what deserves an edit

Require a claim, corroborating evidence, an affected task and a proposed change that preserves the relevant constraints. A diagnostic can locate the question while leaving project intent open. A large document can be appropriate when it is read only for a specialised task. A concise edit that deletes a release constraint fails even if bytes, repetition or warnings decrease.

Example. The root says to run the standard tests and a nested package directs agents to a package-specific integration suite. Check whether running both is intentional for different scopes before deduplicating. Conversely, a script named for read-only checks that invokes a fixing linter is actionable once the project confirms whether the documentation or wrapper expresses the intended contract.

For each proposal, record the expected behavior after the edit, the evidence that will verify it and a protected piece of context that must survive when relevant. Prefer a smaller correction if it achieves the same task outcome without reassigning authority.
